# SEC-002.7 TOTP two-factor authentication

Date: 2026-11-10

Target: stacked on SEC-002 authentication hardening (#106)

## Threat model

- A stolen Hub password is reused without a second factor.
- A TOTP code is replayed within its validity window.
- Recovery codes are stolen from the database or reused.
- A partial password-only login is mistaken for a full Hub session.
- An attacker brute-forces the six-digit challenge.
- MFA secrets are exposed in the database, logs or API responses.
- A user is locked out after enabling MFA or losing a device.

## Design

### TOTP

- RFC 6238 TOTP, HMAC-SHA1, 6 digits, 30-second period.
- Secrets are 20 random bytes, base32 encoded for the authenticator URI.
- Verification accepts the current step and one step either side.
- The matched step is stored in `User.mfaLastUsedStep`; a later attempt at
  the same or older step is rejected as replay.
- Manual secret and `otpauth://` URI are shown during enrollment. No QR service
  or third-party secret exposure is used.

### Encryption at rest

- `MFA_ENCRYPTION_KEY` is a 32-byte key encoded as base64 or 64 hex chars.
- TOTP secrets are encrypted with AES-256-GCM (`v1.iv.tag.ciphertext`).
- Pending enrollment secrets are encrypted too.
- Recovery codes are stored only as SHA-256 hashes bound to the user id.
- No secret, code or token is written to logs or audit metadata.

### Partial authentication

- Password success for an MFA-enabled account issues a separate
  `staark_hub_mfa` cookie (5 minutes, HttpOnly, Secure in production,
  SameSite=Lax).
- The partial token has `purpose: "mfa"`, its own audience/issuer and no Hub
  role. `getSession()` never reads it.
- Only `/api/hub/mfa/verify` accepts the partial token; it validates the user,
  `sessionVersion`, disabled state and MFA state before issuing a full session.
- The partial cookie is cleared on success or expiry.

### Enrollment and activation

1. Authenticated user starts enrollment.
2. Server generates a secret, encrypts it, stores it as pending with a
   10-minute expiry and returns the secret/URI.
3. User enters a current code.
4. Activation confirms the code, promotes the pending secret, generates 10
   one-time recovery codes, stores hashes, increments `sessionVersion` and
   rotates the current session cookie.
5. Recovery codes are shown once.

### Disable and reset

- Requires the current password **and** a fresh TOTP code or unused recovery
  code.
- Disabling clears the secret, pending state and recovery codes, increments
  `sessionVersion` and rotates the current session cookie.
- Other sessions become invalid immediately.
- Recovery-code use does not disable MFA; it consumes one code and issues a
  session.

### Audit

`SecurityAuditEvent` records:

- `mfa.enrollment_started`
- `mfa.enrollment_activated`
- `mfa.enrollment_failed`
- `mfa.verification_succeeded`
- `mfa.verification_failed`
- `mfa.replay_rejected`
- `mfa.recovery_used`
- `mfa.disabled`

IP addresses are SHA-256 hashed. Metadata never contains codes or secrets.

### Rate limits

| Scope | Limit |
|---|---|
| Challenge global | 300 / 5 min |
| Challenge per user | 5 / 10 min |
| Challenge per IP | 20 / 10 min |
| Enrollment per user | 5 / hour |
| Activation per user | 10 / 15 min |
| Disable per user | 5 / 10 min |

All limits use the shared PostgreSQL bucket from SEC-002. A successful
challenge resets the per-user failure bucket.

## Database migration

`prisma/migrations/20261110130000_mfa_totp/migration.sql`

- Adds MFA fields to `User` with defaults/nullable values.
- Adds `MfaRecoveryCode` and `SecurityAuditEvent`.
- Additive only; no existing row is rewritten except new default columns.

## Configuration

```bash
# 32 random bytes, base64 encoded
openssl rand -base64 32
MFA_ENCRYPTION_KEY=...
```

Do not rotate this key without re-enrolling MFA users; existing TOTP secrets
cannot be decrypted after a rotation. Recovery-code disable can work without
TOTP decryption, but the key should still be treated as persistent secret
material.

## Compatibility

- Non-MFA users keep the existing single-step login.
- MFA users get a new verification page after password success.
- Existing `sessionVersion` revocation remains in force.
- Recovery codes are shown once; there is no email recovery channel (no SMS).
- The UI uses existing Hub/Login classes and does not introduce versioned CSS
  classes or redesign completed Hub workspaces.

## Staging verification

1. Enable MFA and confirm the secret/URI works in an authenticator.
2. Confirm the first code activates and recovery codes are shown once.
3. Sign out and sign in: password should return the MFA challenge, not `/hub`.
4. Reuse the same TOTP step; confirm it is rejected.
5. Use a recovery code once; confirm reuse fails.
6. Disable with password + fresh code; confirm old sessions are invalid.
7. Confirm audit rows exist without secrets.
8. Test keyboard/mobile layout of `/hub/mfa` and `/hub/profile/mfa`.

## Deployment and rollback

1. Apply the additive migration.
2. Set `MFA_ENCRYPTION_KEY` in the application environment.
3. Deploy.
4. Run staging checks.
5. Roll back by reverting the code; the added columns/tables can remain. Do not
   delete audit events during an emergency rollback. Existing MFA users would
   need a reviewed disable/reset procedure if the code is rolled back.
